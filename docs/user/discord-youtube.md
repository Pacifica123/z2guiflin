# Discord и YouTube: что проверяется и почему

Профили Blockcheck «Discord desktop», «YouTube default» и «YouTube — автоподбор GoogleVideo» описывают сервис фазами. Фазы идут через И: стратегия
считается полной, только если прошла все обязательные. Адреса внутри одной фазы — ИЛИ: хватает любого.

## Discord desktop

| Фаза | Адреса | Обязательна |
|---|---|---|
| Updater/bootstrap | updates.discord.com, stable.dl2.discordapp.net | да |
| App/API | discord.com | да |
| Gateway | gateway.discord.gg | да |
| Картинки и превью | media.discordapp.net, images-ext-1.discordapp.net | да |
| Вложения и файлы | cdn.discordapp.com | да |
| Voice | discord.media и любые *.discord.media | нет |
| Invite | discord.gg | нет |

- **Войс — следствие.** На практике стратегия, открывшая приложение, gateway и картинки, даёт и рабочий войс,
  поэтому отдельной фазы для него при сканировании нет. Если войс всё же не работает — `--discord-voice-profiles`.
- **Вложения — своя фаза.** Раньше cdn.discordapp.com был ИЛИ-альтернативой media.discordapp.net, и стратегия,
  открывшая только картинки, выглядела полной, хотя `cdn.discordapp.com/attachments/` не отвечал.

### «Картинки грузятся, а вложение — NS_ERROR_TIMEOUT»

1. `ping cdn.discordapp.com` проверяет только IP по ICMP. DPI работает выше: по имени сайта в TLS (SNI)
   и по объёму данных внутри соединения. Удачный ping ничего не говорит о загрузке файла.
2. Discord открывает файлы-вложения во внешнем браузере — так устроен сам клиент. У браузера свой путь:
   Firefox может брать адрес через встроенный DoH и идти по HTTP/3 (UDP 443). Стратегия, подобранная под TCP,
   такой запрос не видит.
3. Кнопка **«Проверить вложения»** в Blockcheck lab (из checkout: `PYTHONPATH=gui python3 -m zap2_gui.adapters.discord_media_probe URL`) проходит
   DNS → TCP → TLS → HTTP → тело для media.discordapp.net, cdn.discordapp.com и вставленной ссылки на вложение
   (ПКМ по файлу → «Копировать ссылку»). Она показывает, на какой стадии всё встало:
   - TLS не завершается или сбрасывается — DPI по имени сайта: нужна другая стратегия для cdn.discordapp.com;
   - соединение открылось, а тело встало на первых ~16–20 КБ — ограничение по объёму на пути. Blockcheck такого
     не видит без `CURL_PAD`; помогает стратегия, которая проходит дальше первых килобайт, или туннель;
   - здесь всё OK, а в браузере нет — разница в браузере (DoH, HTTP/3).

## YouTube: два независимых пресета (1.5.2)

- **YouTube default** (`youtube-basic`, выбран по умолчанию) — цели `www.youtube.com`, `youtube.com`, `redirector.googlevideo.com`, `i.ytimg.com`; обычный статический режим без запросов к тестовому ролику, report_mapping и CDP. Сохраняет старую последовательность фаз.
- **YouTube — автоподбор GoogleVideo** (`youtube-googlevideo-auto`) — та же статическая основа плюс необязательное одноразовое CDP-наблюдение и поиск P1 до запуска Blockcheck. При отказе источников возвращается к статическим альтернативам с предупреждением; это **не** подтверждает доступность реального видео.

Начиная с 1.5.3 preflight также различает `mdig-missing`, `mdig-nss-mismatch` и `dns-resolver-unavailable` по результатам mdig и проверке NSS в том же контексте. Подробности `mdig --verbose` остаются в raw candidate log; резервный DNS здесь не подменяет upstream.

Обе проверки используют upstream `blockcheck2.sh` и одинаковую политику фаз; они не гарантируют обход блокировок. Если до первой стратегии остановился DNS-preflight или sudo, GUI покажет `dns-preflight-failed`, `sudo-start-failed` или `upstream-start-failed`, оставит сырой файл в `Last log`, но **не будет** считать `checks=0` поражением стратегии или продолжать tournament. Исправление настроек DNS/прав проверяется отдельно.


| Фаза | Адреса |
|---|---|
| Сайт | www.youtube.com, youtube.com |
| Видео | узел rrN---sn-XXXX.googlevideo.com, запасной redirector.googlevideo.com |
| Превью | i.ytimg.com |

- Видео поступает с CDN `rrN---sn-XXXX.googlevideo.com`, который зависит от ISP и маршрута.
  В профиле автоподбора P1 ищет до четырёх актуальных кандидатов через `report_mapping` и тестовую страницу YouTube,
  распознаёт кластерные идентификаторы, проверяет DNS (не TCP/TLS) в пределах времени и добавляет
  найденные адреса в фазу «Видео» до резервного `redirector.googlevideo.com`. Это не та же проверка,
  что реальное воспроизведение. При отказе обнаружения используются штатные цели профиля.
  Ручной read-only вызов: `PYTHONPATH=gui python3 -m zap2_gui.adapters.googlevideo_node`.
- www.youtube.com идёт первым: голый youtube.com только перенаправляет на www, и Blockcheck спотыкался о него.
- В Blockcheck lab для пресетов с фазами «Auto-skip dead target» выключен по умолчанию: проверка порта даёт ложный «мёртвый адрес».

## Hostlist

nfqws2 сам учитывает поддомены: строка `googlevideo.com` покрывает все узлы, `discord.media` — все голосовые серверы.
Конкретные узлы в hostlist не пишутся. Строка с `^` в начале отключает учёт поддоменов для этого домена.

При обновлении пакета новые домены доходят до hostlist в установленном workspace: нетронутый файл заменяется,
изменённый получает только недостающие домены в отмеченном блоке. Удалённый вами домен повторно не добавляется.

## CDP-сбор из реального браузера (опционально)

В Blockcheck lab выбери **YouTube — автоподбор GoogleVideo** (либо другой пресет с динамической видеофазой), затем:

1. Нажми **CDP: собрать CDN** и подтверди запуск **отдельного** Chromium/Chrome. Установленный
   `chromium`, `chromium-browser` или `google-chrome` должен быть доступен в PATH.
2. В новом окне открой нужное видео и запусти воспроизведение. Приложение получает через CDP
   `Network.requestWillBeSent`/`Network.responseReceived` только адреса с допустимым именем
   `rr*---sn-*.googlevideo.com` (до 12 хостов в памяти). Работает с вкладками **этого** окна,
   не с уже открытым браузером.
3. Нажми **Завершить CDP** (автолимит 120 секунд либо закрытие браузера). Временный профиль
   будет удалён. GUI покажет обнаруженные имена; **Сбросить CDN** удаляет их без Blockcheck.
4. Запусти штатный Blockcheck. До четырёх прошедших DNS-проверку browser-узлов имеют приоритет,
   P1 дополняет фазу резервными хостами. После передачи адреса одноразово удаляются из памяти GUI.
   При включённой опции DNS precheck явно неразрешившиеся имена отбрасываются; неопределённые
   DNS-результаты остаются допустимыми. TLS/HTTP заранее не проверяются, чтобы не отсеять заблокированный узел.

**Приватность:** требуется явное согласие, обычный профиль Chrome не читается. Chrome 136+
требует отдельный `--user-data-dir`, используется каталог с режимом 0700 и
`--remote-debugging-pipe` (fd 3/4), **не открывается localhost-порт**. Сбор не требует sudo.
Полные URL видеопотоков (включая signature, expire, token), запросы, cookies, HAR и тела ответов
не выводятся в GUI и не записываются в логи приложения. Во время работы временный профиль
существует на диске браузера и может содержать обычные данные сеанса; после окончания
он удаляется. Не входи в личный аккаунт в этом диагностическом окне.

**Ограничения:** отсутствие хостов возможно из-за недоступности сайта, отсутствия видеозапросов,
другого CDN/протокола или изменений Chromium/CDP. Поиск хостов не означает, что video stream
доступен. Исходящие соединения диагностического браузера соответствуют обычному воспроизведению,
а не скрытой сетевой проверке; маршрут/DNS/QUIC могут отличаться от используемого Blockcheck.
Работоспособность конкретной сборки Chromium требует проверки на машине владельца.
