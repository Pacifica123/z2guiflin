# Сетевой вердикт («Диагностика сети (вердикт)»)

Кнопка в Blockcheck lab и отдельный скрипт `gui/zap2_gui/adapters/net_verdict.py`
(`python3 net_verdict.py [--count N] [--blocked host ...] [--json out.json]`).
Задача — подсказать, **в каком слое искать**: локальная сеть, провайдер, DNS или
DPI. Вердикт — гипотеза для текущего момента, а не доказательство.

## Что измеряется

| Слой | Замер |
|---|---|
| маршрут | `ip -4/-6 route show default`, адрес шлюза |
| линк | ping шлюза, 1.1.1.1, 8.8.8.8 параллельно (30 пакетов): потери, дубликаты (`DUP!`), RTT avg/mdev, скачки между соседними ответами ≥ 30 ms, самая длинная серия потерь |
| DNS | системный резолвер (`getaddrinfo`) для example.com, archlinux.org, www.wikipedia.org; при наличии `dig` — сравнение с `@1.1.1.1`; частные/bogon IP в ответе на публичное имя считаются подменой |
| HTTPS | для контрольного хоста (example.com) и «заблокированных» целей (из реестра service targets: YouTube, Discord): DNS → прямой TCP connect к IP:443 → `curl` с фазами `time_connect`/`time_appconnect` |
| контекст | статус zapret (`runtime_session_status`) — активный zapret меняет результат DPI-части |

Отчёт JSON сохраняется в `.zap2/runtime/reports/net-verdict-<время>.json`.
Ничего не требует sudo и не меняет firewall.

## Дерево решений (первое сработавшее правило)

1. Нет маршрута по умолчанию → `LOCAL_NO_ROUTE`.
2. Шлюз: потери ≥ 3 %, mdev ≥ 15 ms, серия потерь ≥ 3 или ≥ 3 скачков → `LOCAL_LINK_OR_ROUTER` (Wi-Fi/кабель/роутер).
   Шлюз, не отвечающий на ICMP вообще (100 %), не считается неисправным — многие роутеры фильтруют ping.
3. Все внешние цели плохие (потери ≥ 5 %, RTT avg ≥ 250 ms или mdev ≥ 60 ms) → `ISP_UPLINK`
   (уверенность high, если шлюз измерен и чистый).
4. DNS: все имена не разрешаются, часть не разрешается при рабочем ping, либо ответ содержит bogon → `DNS`.
5. Контрольный HTTPS работает, а целевой:
   * TCP connect к IP проходит, TLS не завершается (таймаут/RST) → `DPI_SELECTIVE` — зона zapret (SNI/TLS-DPI);
   * TCP connect не проходит → `IP_BLOCK` — десинхронизация обычно бессильна, нужен туннель/другие IP.
6. Всё прошло → `OK`; контроль HTTPS падает при рабочих ping/DNS или данных мало → `INCONCLUSIVE`.

Каждый вердикт содержит строки evidence, уверенность (low/medium/high) и список «что проверить дальше».

## Ограничения

* Снимок одного момента: одна проверка ≠ устойчивый вывод, повторяйте.
* Проверяется только IPv4 TCP/TLS; QUIC/UDP и голос Discord не покрыты.
* Выбор целей определяет результат: «заблокированный» хост может просто лежать.
* `HTTP_FAIL` (обрыв после TLS) трактуется как DPI-признак со средней уверенностью.
* Без `dig` сравнение с публичным резолвером пропускается; подмена DNS на «правдоподобные» публичные IP не ловится.
* При запущенном zapret DPI-часть показывает работу стратегии, а не исходную блокировку.
