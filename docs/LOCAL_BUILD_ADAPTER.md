# Local build adapter

Stage 6 добавляет первый **local build adapter** для vendored-ядра `core/zapret2/`.

## Что это такое

Local build adapter — это тонкий слой нашего GUI/приложения между `BUILD_MAP.json` и будущей кнопкой/экраном сборки. Он не компилирует ядро сам по себе при импорте, не запускает `make` в devctl-проверках и не требует `sudo`. Его задача — превратить уже описанную build map в явный план:

- какую цель собираем: `all`, `nfqws2`, `ip2net`, `mdig` или `clean`;
- из какой директории должна запускаться команда;
- какой `make`-target будет вызван;
- какие артефакты ожидаются после успешной сборки;
- какие системные библиотеки могут понадобиться владельцу локально;
- почему автоматическая проверка не должна выполнять этот план сама.

## Почему это отдельный слой

Мы сознательно разделяем три вещи:

```text
BUILD_MAP.json        фактическая карта Makefile и build units
local_build.py        адаптер, который строит безопасный план локальной сборки
локальная машина      место, где владелец вручную решает запускать make или нет
```

Такой слой нужен, чтобы GUI в будущем не собирал shell-команды из случайных строк. Экран `Ядро` сможет брать план из `gui/zap2_gui/adapters/local_build.py`, показывать его пользователю и только после явного подтверждения передавать выполнение локальному runner-слою, который будет добавлен позже.

## Граница Stage 6

Stage 6 добавляет **планирование**, а не полноценное исполнение сборки. В автоматических проверках запрещено:

- запускать `make`;
- устанавливать пакеты;
- использовать `sudo`;
- менять `systemd`, firewall, `iptables`, `nft` или `ipset`;
- запускать upstream installer scripts.

Разработчик-владелец может выполнить показанную команду вручную на своей машине, если понимает локальные зависимости и состояние системы. Это соответствует общей философии проекта: до `v1-stable` продукт делается для одного пользователя-разработчика, поэтому главный приоритет — прозрачный контроль, а не скрытая автоматизация.

## Текущие команды-планы

Для полной локальной сборки adapter формирует план такого смысла:

```bash
cd core/zapret2 && make all
```

Для отдельного build unit:

```bash
cd core/zapret2/nfq2 && make nfqws2
cd core/zapret2/ip2net && make ip2net
cd core/zapret2/mdig && make mdig
```

Для очистки локальных артефактов:

```bash
cd core/zapret2 && make clean
```

Внутри кода эти команды хранятся не как одна большая shell-строка, а как структурированный `argv` плюс `cwd`. Shell-preview нужен только для отображения владельцу.

## CLI-режим без запуска сборки

Текстовый entrypoint теперь может показать build plan:

```bash
PYTHONPATH=gui python -m zap2_gui.app --build-plan
PYTHONPATH=gui python -m zap2_gui.app --build-plan --build-target nfqws2
```

Эти команды печатают план, но не запускают сборку. Они подходят для devctl-проверок и для первичной диагностики GUI-слоя в headless-среде.

## Что это даёт следующими этапами

После Stage 6 у нас появляется стабильный контракт для развития раздела `Ядро`:

1. GUI может показывать build units и план сборки из одного источника данных.
2. Тесты могут проверять, что план не содержит `sudo`, service/firewall mutation и случайных installer-команд.
3. Следующий runner-слой можно будет добавлять поверх готового контракта, не переписывая inventory/build map.
4. После реальной локальной сборки adapter уже умеет read-only проверять наличие ожидаемых артефактов.

Иными словами, этот патч не “собирает ядро за нас”, но создаёт безопасный мост от инвентаризации к будущей управляемой локальной сборке.

## Связь со workspace-профилями

Stage 7 добавляет профильное поле `buildTarget`. Оно не запускает сборку, а только выбирает, какой target local build adapter должен считать основным для данного workspace-профиля. Например, `default` указывает на `nfqws2`, потому что это основной Linux build unit для будущего GUI workflow.

Валидация профилей проверяет, что `buildTarget` входит в список целей, возвращаемых `supported_build_targets()`. Это связывает слой стратегий с build map без ручного дублирования и без запуска `make`.
