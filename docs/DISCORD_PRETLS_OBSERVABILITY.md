# Discord pre-TLS observability (v0.4-alpha Stage 7n)

Stage 7n pivots the Discord work from another imported strategy toward a
measurable pre-TLS diagnostic branch.

## Why

Owner diagnostics showed the Linux Discord desktop updater stuck in `SYN-SENT`
against Discord/Cloudflare TCP/443 edges. That happens before TLS ClientHello,
HTTP and SNI. A hostlist/SNI strategy can therefore be too late unless the
runtime has a separate way to classify the flow, such as an explicit edge-IP
capture policy or a proven IP→hostname cache.

YouTube still matters as a baseline: it proves the build/runtime path is not
broken globally. It does not prove the Discord updater SYN enters the same
NFQUEUE path.

## Stage 7n additions

- nft queue rules generated by the owner-confirmed runtime apply plan now carry
  `counter` so the owner can inspect whether the rule is hit.
- strategies may declare an optional `capturePolicy` that is separate from
  `runtimeArgs`.
- `capturePolicy.kind=desktop-early-flow-v1` can restrict capture to explicit
  TCP ports and Discord edge IPs, and may opt into diagnostic input SYN+ACK and
  FIN/RST queue rules.
- `community-discord-pretls-diagnostic-pktdebug` is added as an owner-selectable
  diagnostic seed. It is not expected to fix Discord by itself.
- `--runtime-nft-state` prints the generated nft/NFQUEUE snapshot and the manual
  counter command without executing nft or mutating the system.

## Diagnostic loop

1. Select the diagnostic seed:

   ```bash
   PYTHONPATH=gui python -m zap2_gui.app --select-strategy community-discord-pretls-diagnostic-pktdebug
   ```

2. Prepare/confirm/start the normal owner-confirmed Default workflow. For this
   seed, run the privileged start with `ZAP2_RUNTIME_DEBUG=1` so `pktdebug` can
   write to the debug log.

3. Inspect the generated capture plan:

   ```bash
   PYTHONPATH=gui python -m zap2_gui.app --runtime-nft-state
   ```

4. While Discord is stuck on `Checking for updates`, inspect counters manually:

   ```bash
   sudo nft -a list table inet zap2_default
   ```

5. Compare evidence:

   - tcpdump/ss sees Discord SYN but nft counters stay at zero: nft scope is
     wrong.
   - counters move but nfqws2 debug is silent: queue/session attachment is wrong.
   - nfqws2 debug sees the packet but no profile/action is selected: classification
     must be fixed with edge-IP/ipcache policy.
   - action is logged but wire capture does not change: rawsend/reinjection/capability
     must be checked.
   - wire capture changes but Discord stays in `SYN-SENT`: the tried phase-zero
     technique is ineffective or the blocker is below the current layer.

## Safety boundary

Stage 7n remains owner-confirmed. It does not silently broaden default YouTube
capture and does not enable early-flow capture unless the selected strategy has
an explicit `capturePolicy`.


## Stage 7n1 active-state check

Stage 7n1 extends the read-only state view. `--runtime-nft-state` now prefers the
active owner-rules/session metadata when rules are applied, instead of only
rendering the currently selected generated plan. This matters during Discord
pre-TLS experiments because a selected strategy can differ from the strategy that
is already applied and attached to NFQUEUE.

Use:

```bash
PYTHONPATH=gui python -m zap2_gui.app --runtime-nft-state
PYTHONPATH=gui python -m zap2_gui.app --runtime-pretls-probe
```

The probe remains read-only. It does not run `nft`, does not call sudo, and does
not mutate firewall/services. It tells the owner whether the next synchronized
manual check should be counter-focused, session-health-focused, or capture-scope
focused.

Manual counter commands use nft options before the command:

```bash
sudo nft reset counters table inet zap2_default
sudo nft -a list table inet zap2_default
```
